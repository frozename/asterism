# Architecture

Asterism is split into executable entry points, command verbs, adapter contracts, pure domain logic, external-I/O modules, and verification harnesses. The import rules that preserve these divisions are executable checks, not naming conventions (`test/import-boundaries.test.mjs`, tests “(a)” through “(e)”; `test/purity.test.mjs`, test “src/core/ holds files and every one of them is pure”).

## Process entry points and command routing

`bin/ast` is the interactive command entry point. It loads the adapter registry, resolves a verb module from `src/cli/verbs/`, applies the mutating-command refusal and installed-tree identity guards, and passes a shared context to the verb (`bin/ast`, `main`; `src/adapters/index.js`, `adapters`; `src/cli/router.js`, `loadVerb`). With no verb it runs `ls`; with an unknown or syntactically invalid verb it prints usage and returns exit code 2 (`bin/ast`, `main`; `test/cli.test.mjs`, tests for default dispatch and invalid verbs).

Verb modules publish `mutating`, `summary`, and `run` exports. The router derives the available names from `.js` files, restricts names with `VERB_NAME`, checks existence before dynamic import, and allows module errors to propagate instead of turning them into “unknown verb” (`src/cli/router.js`, `VERB_NAME`, `listVerbs`, and `loadVerb`; `test/cli.test.mjs`, router and usage tests).

The command layer is organized by operation rather than by shared side effects. Listing and navigation use the session pipeline (`src/cli/verbs/ls.js`, `run`; `src/cli/verbs/go.js`, `run`; `src/cli/pipeline.js`, `collectSessions`), lifecycle commands use stored records plus the lifecycle model (`src/cli/verbs/park.js`, `run`; `src/cli/verbs/unpark.js`, `run`; `src/cli/verbs/archive.js`, `run`), and creation composes UUID minting, adapter launch argv, tmux spawning, and persistence (`src/cli/verbs/new.js`, `run`; `src/core/uuid.js`, `createUuidMinter`; `src/io/tmuxexec.js`, `newWindow`; `src/io/store.js`, `openStore`).

`bin/ast-hook` is a separate guest entry point. It dispatches bounded event payloads and always exits zero so hook augmentation cannot block the host turn (`bin/ast-hook`; `src/hook/index.js`, `runHook`; `test/ast-hook.test.mjs`, malformed-input and unknown-event tests). The hook import boundary forbids access to tmux keypress paths (`test/import-boundaries.test.mjs`, test “(e) ast-hook and src/hook/ cannot import a keypress path”).

## Adapter boundary and capability records

The registry is a `Map` keyed by adapter id. It always registers the primary adapter and conditionally registers the fake adapter when `ASTERISM_FAKE_ROOT` is a non-empty string (`src/adapters/index.js`, `buildRegistry`; `test/adapter-registry.test.mjs`, registry-shape tests). Adapter directories cannot import sibling adapters or the registry; only the registry composes adapter implementations (`test/import-boundaries.test.mjs`, test “(a) no file under src/adapters/<id>/ imports a sibling adapter or the registry”).

An adapter object combines discovery, hooks, installation, capture recipes, spawn argv, environment markers, static-probe symbols, detection, and an evidence-bearing capability record (`src/adapters/claude/index.js`, default export; `src/adapters/fake/index.js`, default export). The conformance suite enumerates the registry and checks adapter ids, one discovery mechanism, capability validity, detection samples, frozen return values, spawn argv shape, and install-plan availability (`test/adapter-conformance.test.mjs`, parameterized adapter tests).

Capability records use fixed axes whose rungs are ordered from stronger to weaker, plus an explicit `unknown` value. Every known rung carries a grade, probe, and observation date; every unknown carries a probe and deferral (`src/core/caps.js`, `AXES`, `UNKNOWN`, `rank`, and `validateRecord`; `test/caps.test.mjs`, validation tests). Runtime facts may retain or degrade a declared capability but do not improve it; the conformance tests check monotonic degradation for locked-down and older-version samples (`src/adapters/claude/index.js`, `effectiveCapabilities`; `test/adapter-conformance.test.mjs`, tests containing “degrades monotonically”).

Discovery is normalized at the adapter boundary into observation envelopes. `collectObservations` selects an argv-backed lister when present and otherwise selects a function-backed lister, while adapter conformance requires exactly one of those interfaces; the I/O layer returns notes for unavailable sources and adds bounded registry-file enrichment only after filename, size, parse, and peer-protocol checks (`src/io/discover.js`, `collectObservations`; `src/adapters/claude/discover.js`, `discovery` and `ENRICHMENT`; `test/adapter-conformance.test.mjs`, tests containing “exposes exactly one discovery lister”; `test/discover.test.mjs`, discovery degradation and enrichment tests).

## Observation and reconciliation pipeline

The session pipeline gathers observations from every registered adapter, adds binding-spool observations, performs one batched process-table lookup for positive PIDs, and reports degraded inputs as notes (`src/cli/pipeline.js`, `collectSessions`; `src/io/procs.js`, `processTable`; `test/pipeline.test.mjs`, tests “binding spool increments generation” and “pid observations use one batched process-table call”). It then suppresses archived sessions, reconciles active observations, preserves stable ids and Asterism-owned fields from prior records, writes sessions and canaries, publishes the seam index, records usage, and attempts retention cleanup (`src/cli/pipeline.js`, `OWNED_FIELDS`, `stableIds`, and `collectSessions`; `test/pipeline.test.mjs`, archived-session and owned-field tests).

The core reconciler accepts observations from four named sources and groups them by the tuple `(adapter, sessionId)` (`src/core/reconcile.js`, `OBSERVATION_SOURCES` and `reconcile`). For each projected field it selects the newest candidate, then uses source rank and serialized value as deterministic tie-breakers; output records are sorted by status, last-seen time, and id (`src/core/reconcile.js`, `compareCandidates`, `pickFieldWinner`, and `compareRecords`; `test/reconcile.test.mjs`, fold-determinism, merge-precedence, and sorting tests).

Unknown fields, unknown statuses, missing session ids, and unparseable process-start values become SHA-256 canaries rather than silently entering the record shape (`src/core/reconcile.js`, `scanFieldCanaries`, `pickProcStartWinner`, and `reconcile`; `test/reconcile.test.mjs`, open-world, missing-session-id, and proc-start tests). A record without a valid process-start witness is marked `writeDisabled` with pid-only liveness provenance (`src/core/reconcile.js`, `buildRecord`; `test/reconcile.test.mjs`, test “enrichment-absent -- no procStart anywhere means no synthesized epoch, record is read-only”).

The seam exposes a versioned projection of reconciled sessions rather than the full internal record. Its fields are id, adapter, session id, status, waiting reason, last-seen time, and the write-disabled state and reason (`src/seam/index.js`, `buildIndexPayload`; `schema/session-1.json`; `test/schema.test.mjs`, session-schema tests).

## State, identity, and published schemas

State lives under the XDG state directory or the home-directory fallback, while configuration uses the matching XDG configuration rule (`src/io/store.js`, `resolveStateDir` and `resolveConfigDir`). `openStore` sets an owner-only umask, creates the state layout with owner-only directories, and verifies the state schema version before returning a frozen store handle (`src/io/store.js`, `openStore`; `test/store.test.mjs`, permission and schema-version tests).

Typed store writers converge on `writeTextAtomic`: a temporary file is created in the destination directory, its mode is checked, its bytes and descriptor are synced, it is renamed, and the containing directory is synced (`src/io/store.js`, `writeTextAtomic` and `writeJsonAtomic`; `test/store.test.mjs`, atomic-write tests). The structural writer test limits filesystem write sites to the store, configuration editor, and capture writer (`test/writer-chokepoint.test.mjs`, tests “EXEMPT is pinned” and “no fs write call outside”).

Archiving writes and verifies the durable archive copy before unlinking the live record. A failure before removal leaves the source readable (`src/io/store.js`, `archiveSession`; `test/archive.test.mjs`, tests “writes and verifies” and “crash injection after the copy”). Retention separately handles dead-session archiving, archive deletion, inbox expiry, backup pruning, and malformed-record problem counts (`src/io/store.js`, `RETENTION_DEFAULTS` and `sweepRetention`; `test/store.test.mjs`, retention tests).

The installed-tree identity manifest hashes every file under `bin/` and `src/` and records the canonical install path. Mutating commands other than install and uninstall are refused when the stored manifest disagrees with the current tree (`src/io/identity.js`, `buildIdentityManifest`, `verifyIdentity`, and `guardIdentity`; `bin/ast`, `main`; `test/identity.test.mjs`, identity verification tests).

The published session index and handoff formats are version-1 JSON schemas (`schema/session-1.json`; `schema/handoff-1.json`). The in-repo checker supports only its declared keyword set and reports unsupported keywords as errors, while schema tests exercise required properties, enum values, and fail-closed keyword handling (`src/core/schema-check.js`, `SUPPORTED_KEYWORDS` and `checkSchema`; `test/schema.test.mjs`, test “checker handles every supported predicate in both directions and fails closed”).

## Binding and lifecycle models

Binding state is a total transition function over `Unbound`, `Candidate`, `Bound`, and `Poisoned`. Strong witnesses may produce `Bound`, weak witnesses may only produce `Candidate`, pane or process loss produces `Poisoned`, and `Poisoned` is absorbing (`src/core/binding.js`, `BINDING_STATES`, `STRONG_WITNESSES`, `WEAK_WITNESSES`, and `transition`; `test/binding.test.mjs`, exhaustive-table and weak-witness tests). A binding is writable only when its state is `Bound` and its witness is strong (`src/core/binding.js`, `writable`; `test/binding.test.mjs`, writable tests).

Vendor pane witnesses are parsed from the right into window and pane ids, discarding the session name; process ancestry traversal detects cycles (`src/core/binding.js`, `parseVendorPaneWitness` and `descendsFrom`; `test/binding.test.mjs`, parser and ancestry tests). Human and spawn paths persist authoritative bindings through the store (`src/cli/verbs/bind.js`, `run`; `src/cli/verbs/new.js`, `run`; `test/bind.test.mjs`, HumanAsserted binding tests; `test/new.test.mjs`, SpawnMinted binding tests).

Lifecycle state is a separate finite-state machine over `Live`, `Parked`, and `Archived`. Park and unpark are legal only in opposite live states, both live states may archive, and archived records are absorbing (`src/core/lifecycle.js`, `LIFECYCLE_STATES`, `TABLE`, and `transition`; `test/lifecycle.test.mjs`, exhaustive transition tests). `applyLifecycle` writes the lifecycle field, its derived parked flag, and provenance together (`src/core/parkstate.js`, `applyLifecycle`; `test/park.test.mjs`, lifecycle-invariant tests).

## External process and tmux I/O

General subprocess execution flows through `procexec`, which accepts an argv array, uses no shell, captures stdout and stderr, and kills children on timeout or output-size overflow (`src/io/procexec.js`, `procexec`; `test/procexec.test.mjs`, argv, timeout, and byte-cap tests). Structural checks prohibit shell-style exec APIs and restrict `child_process` imports to the two declared I/O modules (`test/exec-ban.test.mjs`, banned-pattern tests; `test/import-boundaries.test.mjs`, test “(b) only the declared exec chokepoints import child_process”).

Tmux calls flow through `execTmux`, which fixes UTF-8 mode, selects an explicit socket, validates every `-t` target, and keeps launched commands as trailing argv data (`src/io/tmuxexec.js`, `execTmux`; `test/tmuxexec.test.mjs`, target and argv tests). The only tmux argv construction sites are the runtime tmux module and the capture module (`test/tmux-chokepoint.test.mjs`, test “(a) a [tmux, ...] array literal appears only in the two declared chokepoint files”).

Socket resolution gathers candidates from the current tmux environment and the two configured socket-directory locations, probes each candidate, canonicalizes the candidate and reported socket, and deduplicates live servers by process id when available (`src/io/tmuxsock.js`, `resolveServer` and `resolveServers`; `test/tmuxsock.test.mjs`, ladder and identity tests; `test/go.test.mjs`, plural-server resolution tests). Parsed tmux output is isolated in pure parsers for panes, clients, and server identity (`src/core/tmuxparse.js`, `parseListPanes`, `parseListClients`, and `parseServerInfo`; `test/tmuxparse.test.mjs`, parser tests).

User-controlled terminal text passes through `untrusted`, which replaces control code points and truncates only at grapheme boundaries using display width (`src/core/render.js`, `untrusted` and `table`; `src/core/width.js`, `displayWidth`; `test/render.test.mjs`, hostile-text and truncation tests; `test/width.test.mjs`, width tests).

## Hooks, installation, capture, and diagnostics

The hook dispatcher accepts only registered adapter/event pairs, reads at most 65,536 bytes, parses JSON, and records errors through the store without propagating them (`src/hook/index.js`, `STDIN_CAP_BYTES`, `readStdinBounded`, and `runHook`; `test/ast-hook.test.mjs`, oversized, malformed, and unknown-event tests). Session-start events write `AgentAsserted` binding witnesses, while notification events deduplicate by payload freshness, persist inbox items before notifying, and prune expired dedupe keys (`src/hook/events/session-start.js`, `run`; `src/hook/events/notification.js`, `dedupeKey` and `run`; `test/ast-hook.test.mjs`, session-start and notification tests).

Installation is represented as adapter-owned plans and applied through the configuration-editing module (`src/adapters/claude/install.js`, `installPlan`; `src/cli/verbs/init.js`, `run`; `src/io/cfgedit.js`, plan and apply functions). Configuration edits are marker-scoped, compare expected bytes before writing, create backups, and restore on post-write mismatch (`src/io/cfgedit.js`; `test/cfgedit.test.mjs`, round-trip, race, backup, and byte-diff-or-restore tests).

Capture recipes come from the tmux capture set and registered adapters. `captureCell` validates the cell id and recipe source, rejects empty captures, scrubs paths and token-shaped values, hashes the scrubbed bytes, and writes `raw` plus `meta.json` atomically within the cell directory (`src/capture/run.js`, `listKnownCells`, `captureCell`, and `writeCellAtomic`; `src/core/scrub.js`, `findLeaks` and `scrub`; `test/fixture-capture.test.mjs`, validation, scrubbing, and atomicity tests). Tmux capture runs use a fresh labelled server, record the reported socket, and refuse success if cleanup leaves that socket present (`src/capture/tmux.js`, `buildTmuxPlan` and `runCell`; `test/fixture-capture.test.mjs`, tmux cleanup tests).

Diagnostics are the checks registered in `CHECKS`; each returns `pass`, `warn`, `fail`, `todo`, or `unknown` (`src/doctor/index.js`, `STATUS`, `CHECKS`, and `runDoctor`; `test/doctor.test.mjs`, registry and per-check tests). The doctor command renders all results and returns the aggregate outcome defined by `runDoctor` (`src/cli/verbs/doctor.js`, `run`; `src/doctor/index.js`, `runDoctor`; `test/doctor.test.mjs`, exit-status tests).

## Enforced repository boundaries

The `src/core/` layer may import only other core modules and permitted pure built-ins; it cannot read process environment or import filesystem, process, network, operating-system, or package modules (`test/purity.test.mjs`, purity sweep and synthetic controls). Product code cannot import test or harness modules, adapter implementations cannot cross-import, hook code cannot reach keypress modules, and seam paths cannot reach tmux execution (`test/import-boundaries.test.mjs`, tests “(a)” through “(e)”).

The refusal ledger is a frozen list of rules R1 through R9. The executable path applies R5 to mutating commands invoked inside an adapter-marked environment and applies R9 through installed-tree identity verification (`src/core/refuse.js`, `REFUSE_RULES` and `refuseIfAgentInvoked`; `bin/ast`, `main`; `test/refuse-rules.test.mjs`, rule and marker tests; `test/identity.test.mjs`, guard tests).

Repository tests enforce zero runtime and development dependencies, bare test-runner discovery, ignore-rule effects, and secret scanning of Git-visible files and commit messages (`test/no-deps.test.mjs`; `test/test-discovery.test.mjs`; `test/ignore-rules.test.mjs`; `test/repo-hygiene.test.mjs`; `harness/secret-scan.mjs`, `scanText`, `listFiles`, and `listUnpushedCommits`). CI runs the same suite under Node and Bun in independent jobs (`.github/workflows/ci.yml`).

The mutation harness copies the executable tree and tests into an isolated directory, applies each exact single-match replacement, runs only the claiming tests, and reports `killed`, `survived`, `unapplied`, and `unclaimed` outcomes (`harness/mutants/run.mjs`, `runMutant` and `runAll`; `test/mutants.test.mjs`, mutant-shape, anchor, and outcome-control tests). The curated mutant list assigns each changed predicate to the test expected to reject it (`harness/mutants/mutants.mjs`, `MUTANTS`).
